# PR #24：迟到恢复与参数一致性复核

本文记录 `47b0aef` 到 `340e510` 的 V5 复核；后续关键视频配置升级到 V6，见 [关键视频制动等待](37-critical-video-braking-recovery.md)。

复核基线为 `47b0aef`。处理规则、控制端配置入口和恢复通知共同组成一套机制，800 ms 是独立的持续无有效控制保护。

## 规则和两端恢复

- 默认连续迟到阈值 3，范围为整数 1–5。超过 200 ms 的命令不执行，重复/乱序/错身份不累计。
- 阈值之前的新有效帧可以恢复可恢复降级；300 ms 降级撤牵引，但保留当前会话参数。
- 达到阈值后，车端锁住非零牵引/转向；原生 delivery ACK 将这个结果交给云端，再随独立字段返回控制端。
- 控制端立刻撤掉旧运动输入，要求新零输入。车端实际应用零运动输入后解除本地降级；控制端确认完整零输入后解除自身运动锁，释放旧方向键再按可以继续使用同一参数修订号。
- 旧媒体通知通过控制状态序号及车端已接受命令序号去重。云端入口 ACK 本身不代表车端执行。
- 1 帧保留严格模式：收包间隔超过 200 ms 也要求重新输入；控制端帮助文字明确说明这个差异。

## 参数一致性

控制端和车端 C++ 共用 `kSessionControlProfileVersion=5`，页面使用 V5 严格字段清单。迟到帧数、驻车延时以及其他 PID/速度/转矩/压力/转向字段都参与精确 ACK 比较；请求序号、应用修订号、会话和权限门禁也必须匹配。

车端在适配器成功应用参数、修订号正确且实际接收器已设置迟到阈值后，才返回接受结果。首次设置和迟到帧数变更需停车、N、零速、EPB 和 standby/disarmed（或隔离 mock 台架）。

复核增加控制端实际 HTTP 请求 -> 车端解析/应用 -> 全字段 ACK 的 1–5 回归，并检查未驻车拒绝时实际阈值保持旧值。遗漏新字段、V4、非整数版本均被拒绝。页面/C++ 版本一致性也纳入 Node 测试。

底盘 V3 函数的 scalar ABI 使用版本 4；这是独立的底盘接口版本。V5 会话配置由车端服务管理，迟到计数不交给底盘 ABI，因此映射为 4 不会导致页面参数 ACK 不匹配。

混装 V4/V5 或保留旧页面仍可能无法驾驶，会被明确拒绝；必须更新同一提交的云端、车端、驾驶端，重启驾驶程序并重新打开页面。

## 800 ms 的准确含义

从车端最后一次通过校验并成功应用控制命令起算。零牵引/零转向心跳、仅制动命令同样可以是有效控制；过期、重复、错身份和被门禁拒绝的包不重置时间。

因此正常 800 ms 不按键不会触发链路超时。控制端持续周期发送零输入，车端持续接受；“无操作自动驻车”使用独立的 `parking_idle_timeout_ms`，默认 500 ms。输入租约（默认 200 ms）和云端 ACK 活性也各有独立计时。

持续 800 ms 没有有效控制会撤销参数并开始安全停车；网络恢复不自动恢复牵引，必须重新确认驾驶权限。

## 本轮发现并修复

`47b0aef` 的原生重新输入分支沿用全输入失效，会把仍按住的普通刹车清零。先用 portable NativeControlIntentStore 回归复现，再修复为仅在车端可恢复重新输入、输入租约仍新鲜时保留制动。仅制动请求可持续更新，但不解除运动锁；键盘 Space/B 和手柄制动保持，旧方向键或手柄运动必须先归零。

真正输入租约过期、页面替换、失焦、运输重连、急停和权限撤销使用原有保护；不执行过期普通制动，不恢复旧牵引。页面区分车端重新输入与输入租约失效的提示。

同会话重新打开页面时，页面内输入序号从 1 开始，旧反馈的输入序号可能较大。原实现将两者直接比较，会误报反馈非法并重连。新增回归先复现，再改为用会话内单调命令序号、实际已发/已交付范围和参与方身份核对；输入序号保留作关联，不跨页面比较大小。错误会话和未来命令序号仍被拒绝。


## 验证边界

回归通过真实本地云端和驾驶端 WebSocket、实际车端控制服务及 mock 适配器：先应用持有命令，注入三帧迟到，验证原生通知、车端零运动恢复、持续制动、完整零输入后新牵引再次被车端接受，参数修订号保持原值；没有依赖媒体 DataChannel。

另覆盖持续一分钟零输入心跳不会触发 800 ms，停止心跳后第 799 ms 不撤参数，第 800 ms 进入超时停车。

这些是软件链路和 mock 执行证据。未连接现场车辆，不能替代 VCU 反馈、网络条件、PID、驻车/制动机构及真实牵引验收。
