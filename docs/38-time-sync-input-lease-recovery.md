# 时间同步、输入租约与视频的制动恢复

## session-000070 的证据与软件问题

附件六个 ZIP entry 均成功解压并通过 CRC。导出 manifest 标记为 partial，CAN 文件达到
64 MiB 上限，最后记录 UTC 2026-10-13 03:12:56.725，早于首次故障；因此不能确认该次
物理 EHB/EPB 动作完成。下述时间均为 UTC，不能混用现场时区。

- runtime.log 第 1141 行在 03:14:08.641 记录 `vehicle_media_pipeline_failed`，issue 为
  `media_runtime_time_sync_uncertainty_exceeded`：不确定度 26 ms 超过 25 ms，选取 RTT
  51 ms、7 个样本、offset -15 ms。26 ms 是校时不确定度估计，不是实际时钟偏差。
  浏览器第 2518 行收到相同原因与 adapter_ready=false。旧路径把短暂校时超限直接变成
  公共管线故障并撤销会话控制，本轮将该可恢复条件改为独立制动等待。
- seq 5393 在 03:14:06.634 最后成功应用运动；seq 5394 回调 06.720 进入、等控制 mutex
  1920 ms 后于 08.641 因 runtime_stop_requested 拒绝。该等待与故障关闭路径重叠，
  不是首次停车由独立 watchdog 引起的证据。
- 03:14:04.386 最近媒体状态中关键 ccg2_channel_0 采集仍推进，编码年龄 85 ms，
  lane active、failure=0；未见 critical_camera_failed。多路编码队列占满值得继续调查，
  不能据此改判首次停车为相机故障。03:16:18 的 SCTP 失败发生在 driver_logout 后。
- 页面在 03:12:25.270、03:13:09.266、03:13:40.102 清除输入，原因均为
  native_intent_rearm_required；原生 trace 已出现 fresh=false、requires_fresh_input=true。
  真租约过期清除旧运动输入正确；旧日志没有逐次校时耗时，不能唯一归因每次过期。
- 代码确认 `/api/status` 同步执行网络校时与重复控制权续租。监控请求占用本地 HTTP
  处理路径时，慢采样可超过 200 ms 输入租约；已有专门续租 worker，应从监控路径删除
  网络工作。另一个缺陷是 update 入口未核验上一输入年龄，延迟刷新可抢在下一次
  sender sample 前续上已过期的运动；新增入口检查堵住这一竞态。

该现场 profile 为旧 V5，实际 control_timeout_ms=2000，本轮不把它改成 800。
网络 RTT/不确定度超限的根因仍未唯一确定，不能声称修复了无线链路、GPU 或硬件。

## 当前恢复与安全边界

视频、时间同步与输入租约复用同一个会话级恢复状态机，不新建互相覆盖的等待时钟：

1. 关键采集故障立即制动；关键编码/显示无新帧达到配置门限制动；任一端校时超限或
   采样失败、驾驶端真实输入刷新过期也撤牵引并制动，保留会话、已确认参数和控制服务。
2. 校时移至独立 worker/独立 500 ms HTTP client。`/api/status` 只读本地状态；坏采样
   更新最新不可信状态，保留最后可信 UTC/steady anchor 与采集时间戳转换 offset。
   控制禁止运动，继续发送经过身份、序列、年龄、当前挡位验证的真实零运动心跳；
   不能执行过期运动，也不能让错误校时跳变编码 PTS。
3. 所有条件恢复、全部关键编码/显示至少 3 个新帧且健康持续 300 ms 后请求新鲜零输入。
   老按键和手柄输入不会自动复活。零输入仍保持独立安全制动；重新按下的新运动被
   适配器成功接受后才解除该保持，拒绝换挡或执行器拒绝不会提前松开制动。
4. 首次故障的等待截止时间冻结。交替故障、好帧、参数变化和同会话 runtime 重建
   不延长截止时间。超时进入硬安全停车，仍需结束旧会话、重新建立参数和 VCU 握手。
5. 独立控制 watchdog 默认 800 ms 从最后成功接受并应用的真实命令起算，现场已有
   配置另行决定。没有有效新命令达到该门限仍停车，不等统一恢复的 5 s。
   本地制动与坏包不能续期；不按键但持续有合法零心跳不会触发此断链超时。
6. 输入租约 200 ms、命令年龄 200 ms、校时可信上限 25 ms、身份/序列/挡位门禁不放宽。
   CAN、物理急停、权限丢失、不可隔离公共传输故障和制动执行失败仍沿原硬保护路径。

控制延迟导致 DEGRADED 时沿原可恢复门禁执行；普通迟到阈值默认 3、范围 1–5 帧，
过期包始终不执行。真正长期无有效控制的 watchdog 与输入刷新过期是不同条件。

## 配置、匹配与黄色提示

- “实车调试限幅”中的 **控制故障恢复等待上限** 使用 `control_recovery_timeout_ms`，
  默认 5000 ms，整数 1000–30000 ms，页面以秒输入；视频无新帧制动仍使用
  `critical_camera_stale_brake_ms`，默认 500 ms，范围 100–3000 ms。
- 完整 V7、17 字段必须停车、N、零速、EPB 与 standby/disarmed（或隔离 mock 台架）
  后提交并逐项精确 ACK，页面显示确认值。V6 及更旧版本明确拒绝。
  驾驶端、云端和车端一起更新；旧云端解析转发会丢失新 readiness 字段，新车端拒绝
  缺字段普通控制，不默默忽略。鉴权急停不依赖新字段。物理桥 ABI 和 DBC 没有变化。
- 旧 YAML `critical_camera_recovery_timeout_ms` 是兼容别名；新旧字段同时填写且不同
  会拒绝启动。车端默认值预填页面，但不会自动提交参数。
- 主视频区新增黄色条，以车端 `control_timing.control_braking_wait`、
  `control_recovery_cause`、`recovery_brake_hold` 与 DEGRADED 反馈区分关键视频、
  时间同步、输入过期或控制延迟；恢复后显示“链路已恢复，制动保持”与释放重按。
  新运动解除保持后自动隐藏。红色安全停车/急停优先。
- 反馈超过 500 ms 时明确显示“此前已报告…当前制动状态待确认”，不把旧反馈说成当前
  已制动/已停稳；页面本地 RTT 或视频指标单独恶化不作为车端已制动的确认。

## 日志与软件验证

车端新增/统一 `vehicle_control_braking_wait`、`vehicle_control_recovered`、
`vehicle_control_recovery_timeout`，记录首次原因、门限、稳定时间、单调截止时间、
最新校时状态和安全动作；native trace 的 `time_sync_refresh` 记录持续时间/错误与
是否接受 anchor。驾驶端 `intent_received` 与发包 trace 记录 intent_age_ms、
intent_lease_ms、接受/拒绝原因、健康标志与有效运动值。日志不携带控制 token。

回归覆盖真实慢 `/time` 服务下 status 不阻塞、持续输入未过期、坏/好校时在同会话恢复；
坏采样/失败不替换 UTC anchor 或采集时间线；真实输入租约过期与迟到 ingress 竞态；
实际零心跳保持独立制动、普通压力限幅为零仍制动、恢复零输入不松刹、适配器拒绝保持
制动、新运动成功后恢复、混合原因/参数/重建不延长 deadline，以及独立 800 ms 门限。
黄色条覆盖各原因、过期反馈、红色优先、恢复保持与最终消失；实际构建页面在本地
模拟 API 与 Chrome 中检查桌面/移动显示、配置/精确 ACK、释放重按与同会话保留。

Docker/fixture/浏览器结果只证明软件路径；最终数量与跨平台 CI 见 PR #24。
