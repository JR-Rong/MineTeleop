# 临时制动、硬停车及全非关键相机配置复核

本次以 PR #24 的 `dc26eca` 为基线检查生产代码，并修改全非关键相机配置。
没有本次新现场日志，不能把此前会话中的频次当作该版本实车结果，也不能仅凭
“连接仍在”认定控制链路健康。本文区分撤牵引、可恢复制动、硬停车和普通控车门禁。

## 进入临时制动或撤销运动的条件

| 条件与来源 | 当前触发条件 | 动作、恢复及评估 |
| --- | --- | --- |
| 车端关键视频输出不新鲜，`webrtc_media.cpp::enforce_control_recovery` | 任一启用关键相机的编码帧年龄超过协商门限；默认 500 ms，可配 100–3000 ms | 独立制动并保留会话/profile；至少 3 个新编码帧且所有 readiness 稳定 300 ms 后恢复。保护失去驾驶视野有用途，但八路全部关键时是“任一路失败就制动”，实际可用性很敏感。采集有帧不代表编码/网络/呈现有新帧。 |
| 车端明确关键采集/编码故障 | 关键 lane faulted/disabled，或故障处理直接 `pause_control_for_critical_camera` | 立即制动，不等待 500 ms；故障重开成功也需新帧和稳定观察。非关键 lane 故障仅重开/停用该 lane，不直接进入视频制动。共享媒体 pipeline 致命失败仍可能关闭控制，不能用相机 critical 设置屏蔽整个进程/管线失败。 |
| 驾驶端关键画面不可用，`camera_view.js::criticalHealth` | 任一关键 track 缺失、mute、ended、peer 断开、无呈现帧、呈现帧超过协商门限，或恢复帧不足 3 | 页面清除/阻止旧运动，原生命令报告 `critical_video_ready=false`，车端独立制动。明确 track 状态异常可立即撤销健康；1 s 遮罩显示期限不是制动期限。它保护“车端在出帧但驾驶员看不到”的情况，也会受浏览器解码/呈现停顿影响。 |
| 驾驶端本地输入租约过期，`NativeControlIntentStore` | 默认 200 ms 内没有成功更新本地意图；HTTP 排队、UI 长任务、页面后台/冻结或进程停顿均可能导致 | 旧运动作废，原生发送零运动并报告 `operator_input_ready=false`；车端独立制动。不是“人 200 ms 没按键”，长按与空闲都依赖自动心跳。失效旧长按不能在网络恢复时自动复活；页面及时补新零意图后可恢复，继续运动须释放重按。200 ms 对桌面调度敏感，不能先把它认作移动网络故障。 |
| 驾驶端或车端校时不可信 | 未同步/采样失败，或不确定度超过两端默认 25 ms；车端 `require_time_sync=true` | 立即禁止运动并进入制动等待，保留上次时间映射锚点而撤销其运动授权。坏 HTTP RTT 样本不是时钟已损坏的证明。25 ms 是项目工程默认值；此前 RTT 124–192 ms 的公网样本不适配该准入预算。 |
| 原生控制 ACK 返回停滞，`NativeControlAckRecovery` | 有待确认包且合法累计 ACK 连续 500 ms 不推进 | 冻结挡位、撤销旧输入并请求车端制动，保留当前 WSS；新 ACK 确认年龄 ≤200 ms 且持续推进 ≥300 ms 才恢复。正常高延迟但持续推进的 ACK 不单凭 RTT 进入等待；已经等待后，持续高 RTT 会妨碍退出。ACK 不是车端 CAN 实际执行确认。 |
| 命令过期或接收间隔退化，`ControlReceiver` / `SafetyStateMachine` | 包 UTC 年龄 >200 ms 时始终丢弃；默认连续 3 条不同序号迟到要求重激活，可配 1–5。有效控制间隔 ≥300 ms 进入 DEGRADED；配置为 1 帧时首条 gap >200 ms 还会拒绝 | 这些是撤牵引/要求零输入的条件，不全都等同独立全制动。普通 DEGRADED 保留原 steering/brake，撤 throttle；恢复等待则使用独立制动。新鲜零输入可重激活，未必要断开会话。单条过期命令不执行，但不是单条立即硬锁。 |

方向冲突、换挡等待、缺少 profile ACK、VCU 尚未 ready、鉴权/控制权丢失、窗口失焦
清键也可能表现为“按了页面有反应但车不走”。这些普通门禁或主动零输入不能全部
计为车端临时制动事件。页面黄色条依赖车端反馈；本地输入被清除本身不是实车制动验收。

共同恢复规则由 `SessionControlRecoveryLatch::observe_recovery` 仲裁：默认首次制动
后 5 s 内所有 readiness 持续健康 300 ms 才退出；profile 可配恢复期 1–30 s。
截止点在该次等待开始时冻结。视频、校时、输入、ACK 交替失败时不会重新计时，
因此每个故障看似短暂、但始终没有 300 ms 的共同健康窗口，也可能最终锁会话。
日志中的 recovery cause 是首次原因，必须结合当时四项 readiness 与 critical_lanes
看当前阻碍，不能把首因当作整个等待期间的唯一故障。恢复后允许自动零心跳长期
保持制动；无需驾驶员在 2 s 内重新按键，旧长按仍需释放重按。

近期 `8a683d0` 将校时/输入异常纳入保留会话的制动等待，`a952814` 为 ACK 增加
同类等待；此前直接失效/重连的情况现在更容易被记录为临时制动。更多状态转换
本身不能证明阈值变严，也不能证明稳定性已变好。反复要求重新输入确实会降低测试
可用性，需结合运行版本与触发原因逐项改善。

## 此前日志能证明什么

session-000008 的有效 profile 期间有 41 次进入制动等待的状态转换：33 次视频
（23 次驾驶端画面报告、10 次车端输出不新鲜），8 次输入租约。不是 41 次物理停稳。
关闭所有视频控制关键标志可以消除这类直接视频保护；不会消除编码负载、控制发送
排队或输入刷新问题。输入并发刷新、过期/乱序 HTTP 响应处理、ACK 两次发送之间
的 20 ms 非阻塞读取已在基线修复；缺少新版本现场日志，尚不能宣称它们已解决频繁停车。

首次硬停车前，2607 仍被接受（年龄 192 ms），随后包年龄 215、243、436、508 ms，
包持续到达但超过 200 ms，最终达到该现场配置的 2000 ms“无合法成功应用控制”。
驾驶端发出到云端接收的 UTC 差值从 146 增至 455 ms，云端 mailbox 等待最大 49 ms，
车端锁等待 0 ms、接收处理最多 1 ms。支持该区段存在持续延迟，不能证明整个网络

## 为什么不能只保留相机硬停车

当前硬保护包括：

- 默认 800 ms、现场附件配置 2000 ms 无合法且成功应用的新控制；该时钟用 steady_clock，
  迟到/错身份/未通过重激活/执行失败的包不能续期。程序仍发包、TCP 显示连接并不能
  证明底盘正在收到新鲜且可执行的控制。
- 会话 readiness 恢复期限到期（默认 5 s），或 ACK 有界等待到期/真实 socket 与协议错误
  导致重连，进而可能造成车端无有效控制。ACK 的 128 未确认包上限也是独立恢复边界。
- 物理/人工急停、CAN 反馈缺失、执行器或制动应用失败、底盘握手故障、硬超速、会话
  失去授权/结束、共享运行时致命故障。这些即使所有相机非关键也必须独立处理。

有必要停止执行失去新鲜度证明的控制，且实际制动链路失效必须有硬保护。
“停止运动”和“撤销会话、必须重连”是两个独立设计决定。对已经成功独立制动、持续
接收合法认证零心跳、硬件反馈正常的纯时间/输入/ACK 异常，可以评估继续保留会话，
让可信状态和新输入恢复后继续；这需要明确新规则并验证制动/挡位保持、反馈和恢复，
不应通过关闭所有 watchdog 或让过期运动包续期实现。
此前用户确认保留校时故障默认 5 s 升级，本次只评估，不悄然取消该规则。

## 校时和最新命令策略

当前异常校时已跳过正常 30 s 刷新间隔并每 100 ms 检查重试；独立 worker 的每次
HTTP 上限 500 ms，通常一组 7 次串行采样（配置允许 3–15），因此重试并非 100 ms
就一定获得可信结果。已有失败组诊断与请求/锁/TCP 分阶段日志。
取得可信组后仍需共享 readiness 稳定 300 ms 和新零输入。25 ms 不确定度大致要求
最佳网络 RTT 不高于 50 ms，持续不达标时只加快重试无法解决准入问题。

可进一步在恢复阶段收齐至少 3 个完整有效样本且按现有误差包络通过门限后提前结束
该组，避免等待其余采样；正常统计仍完成配置组。这是后续可验证的优化，不代表
单样本可信，也不能采用不完整组、提高门限或无限沿用旧锚点来授权运动。
更根本的改进是审查控制路径和可信时钟/新鲜度预算；直接提高两端不确定度会侵占
200 ms 包年龄预算，需重新验证而不是仅改一个数。

普通运动指令已按最新状态处理：浏览器有限并发加一个最新待发状态、原生意图只存
最新序号、云端 `latest_control_messages_` 每接收者一个槽位替换、车端一个 envelope
选最新合法命令；合法急停不按普通过期/合并规则丢弃。旧包仍需接收解析后才能丢弃。
这种应用层合并不能跳过 TCP/TLS 在 socket/代理中已有的有序积压，也不保证最新包
抵达时仍在 200 ms 内。诊断应以发送/云端接收/转发/车端回调和 apply 边界定位，
不能把“最新序号”当作“新鲜时间”的替代。

## 本次实现与配置方法

车端 YAML 对所有启用相机显式设置：

```yaml
cameras:
  - id: ccg2_channel_0
    enabled: true
    critical_for_control: false
    # 保留该相机其他 device/profile/capture 配置
```

其他启用相机同样设置 false；未写该字段仍默认 true。没有至少一个 critical=true
的要求，但仍要求至少一个启用相机。默认/现场示例不自动改为全部非关键。
更新车端程序及 YAML 后按既有停车更新流程重启并建立新会话，页面读取车端 lanes。
当前驾驶端已有明确“所有 lane 为 false”处理，不新增 profile/协议必需字段，云端无需
因该项更新。空/缺失/未知相机元数据仍按未知状态阻止运动，不能冒充显式关闭保护。

车端 `VehicleControlService` 由启用相机计算 `critical_video_required`；没有关键相机
时忽略视频 readiness=false 对该 gate 的影响，其他 readiness、命令年龄、watchdog
和物理急停仍独立有效。control_timing 输出 `critical_video_required` 与有效
`driver_critical_video_ready`，原始报告仍在接收 trace 中，可判断配置是否生效。
画面中断/暂无新帧提示保留，非关键遮罩仍为 3 s；该设置仅取消相机视频对控车的直接保护。

连续 10 s 视频 false 报告仍可执行新鲜运动、校时/输入/ACK 仍制动、独立 800 ms

全 false 和单路恢复 true 后重新保护，已有画面冻结/遮罩回归继续执行。

- Reuse：采用现有相机配置、readiness、制动和诊断，未增加另一套保护状态机。

- Efficiency：相机关键性只在服务构造时计算；控制热点仅一项布尔判断，无逐帧新增日志。
