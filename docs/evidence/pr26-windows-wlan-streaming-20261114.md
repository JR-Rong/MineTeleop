## Candidate borrowed from Moonlight

Moonlight requests Windows WLAN media streaming mode for connected wireless interfaces, and releases that client request by closing its WLAN handle. See [the implementation at `94c65fd`](https://github.com/moonlight-stream/moonlight-common-c/blob/94c65fd364d17b223f00a8763c9a5d94a66cb8dd/src/PlatformSockets.c#L849-L938), [Microsoft's opcode contract](https://learn.microsoft.com/en-us/windows/win32/api/wlanapi/ne-wlanapi-wlan_intf_opcode) and [the API](https://learn.microsoft.com/en-us/windows/win32/api/wlanapi/nf-wlanapi-wlansetinterface). This is a platform hint intended to reduce wireless streaming jitter; effectiveness depends on the driver and is not guaranteed.

`ScopedWifiStreaming` implements a best-effort, client-owned request without changing persistent adapter settings. The browser controller owns it while its application runs; the native viewer owns it during its connection worker. The optional system DLL is loaded from System32. Missing WLAN services or unsupported drivers report an error and preserve existing control behavior. Startup diagnostics record counts/error codes, not interface identities. No WLAN calls run in the periodic control sender. Closing the owner releases its handle; network reconnection can reset the driver mode and is not claimed to be covered by this startup hint.

On the actual Windows device, a short API check observed mode **0 → 1 → 0**, with both set and close returning success. A temporary API wrapper with the original Wi-Fi 6/power settings then completed 17 directional cycles, but failed the continuous-direct criterion at 428.422 seconds when commands switched to WSS. The sampled vehicle state at failure was still `CONTROL_ACTIVE` with stop sequence zero; this is not evidence of a safety-stop failure or of a completed 15-minute run. That wrapper is a prototype and does not validate the new compiled C++ implementation.

While streaming mode was active, querying the separate background-scan flag still returned enabled. A short independent API check successfully changed that flag **1 → 0 → 1** using its own client handle. The candidate therefore also requests `wlan_intf_opcode_background_scan_enabled = FALSE` on connected WLAN interfaces. This is a separate Windows API request, not a claim that Moonlight makes the same additional call. It does not disable WLAN auto-configuration, change the Wi-Fi protocol, alter VPN, or persist registry settings. It is released by closing the same client handle. Suppressing background scans may affect discovery of a better access point; roaming behavior has not been validated. Unsupported requests remain best-effort and are visible in startup error/count diagnostics.

## Paired packet-timestamp evidence

Windows Packet Monitor observed the physical WLAN component with a 62-byte snapshot, while an Orin packet socket recorded only incoming DTLS header identities and kernel timestamps. No command body or video payload was retained. Calibration showed that Windows capture coverage was incomplete, even without ETW lost-event reports. Missing records therefore cannot be treated as packet loss or used to estimate full-path gap distributions.

The exported PCAPNG advertised Ethernet, but its actual frame bytes were native 802.11. The analysis validates frame type, header length, LLC/SNAP and IPv4/UDP headers before joining nonzero IP ID + UDP ports + declared UDP length to the Orin metadata. It matched 4,695 observed DTLS packets. These are a captured subset, not a complete network-delay distribution. Windows timestamps were corrected using accepted signaling-clock anchors with uncertainty at most 25 ms.

One observation at the failure had IP ID 41880, UDP ports 61664→37392, UDP length 1013, and Orin DTLS record sequence 42564. Windows NIC observation was `1794726649335.325` ms; after the nearest accepted clock offset of -596 ms it was `1794726648739.325` ms. Orin kernel arrival was `1794726648943.392` ms, a **204.067 ms** difference. The nearest anchor uncertainty was 11 ms; surrounding offsets were -593/-596 ms. The observation point is delivery to the NIC component, not proof of actual radio transmission. This supports delay after the Windows capture point, and is incompatible with an explanation confined to the Orin application callback. It does not distinguish driver queueing, radio retries, AP or the intervening LAN. Encrypted DTLS was not decoded to assign this packet to one particular control command.
