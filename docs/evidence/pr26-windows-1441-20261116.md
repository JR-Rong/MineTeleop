# Authorized MT7921 1441 trial: startup failure, 2026-11-16

**Result: Windows crashed during the driver-change window. Zero scored control
cycles; no latency comparison or 60-minute acceptance.** The user explicitly
authorized this temporary driver trial and restoration. No reboot command was
issued. VPN and all safety thresholds were unchanged; no physical control was
performed.

## Crash evidence and attribution limit

The original trial snapshot was written at 12:16:27 UTC. Windows' last boot
was 12:17:14.500 UTC (04:17:14.500 America/Los_Angeles). Event 1001 at
12:17:29.230 UTC reported:

- Bugcheck `0x0000007e`, exception `0xffffffffc0000005`.
- Exception address `0xfffff8029243a4b1`.
- Minidump `111626-15156-01.dmp`, 1444793 bytes; retained privately on Windows.
- Kernel-Power 41 and unexpected-shutdown 6008 accompanied the new boot.

The matching WER signature's exception address was the same, and its bucket
was `AV_ACPI!ACPIIrpDispatchDeviceControl`. Another recent WER report also had
this bucket but a different exception address. A bucket identifies an observed
failure location, not the calling driver or root cause. No complete symbolized
kernel stack was obtained in this receipt. Neither MediaTek culpability nor a
shared cause with the earlier 491 ms receive gap is established. The observed
crash is sufficient to reject this driver trial on this machine; it is not a
reason to keep 1441 installed for a longer test.

The installation action receipt's first 210 bytes were zero-filled after the
crash. They were preserved as-is; no successful install-return/reboot flag was
invented from them. Later live PnP/runtime readbacks establish only that 1441
had become active. The boot interruption explains why the interactive test
launcher could not run: no user desktop was logged in afterward.

## Restoration and cleanup

The original recovery tasks used interactive logon. After the crash, the
restore task needed revalidation in the live scheduler; merely finding a task
XML file was insufficient. A re-registered guard kept the original
13:46:27 UTC deadline, but interactive tasks could not execute without a user
session. This limitation was detected before any control test started.

Recovery was instead launched with an explicitly verified SYSTEM service-account
task, using the same hash/signature-checked original backup and an explicit
backup path independent of SYSTEM's profile. It did not need a desktop logon,
change VPN, or reboot the system. The driver restoration action returned
success at 12:26:39.309 UTC with `RebootRequired=false`. Original binding/runtime
1336 / `oem50.inf` and all saved advanced properties were restored; candidate
`oem61.inf` was removed with exit code 0. The bounded task's later idempotent
invocation found no further candidate package to remove.

Full readback at 12:27:42.885 UTC verified:

- Original 1336 runtime, all 14 original public adapter properties, including
  AX=0, Auto=0, roaming=4 and LowPowerEnable=1.
- Original power plan, WLAN AC/DC 0/2, EnergySaver AC/DC 0/30 and device auto-off
  Enabled; no managed power journal.
- No test route or owned control/browser process; WPR and PacketMon idle with
  no filters.

Two inactive A17 preparation tasks and the dedicated Windows test credential
were removed. The inactive SYSTEM recovery task was removed after completion.
An orphan driver-install task XML remains as a private crash artifact; it is
absent from the live scheduler and was not manually removed from Windows'
system directory. Original driver backups and permanent SSH keys are retained.
The isolated Orin services were stopped and CAN remained down. Temporary test
credentials/private keys are cleaned after evidence archival.

## Acceptance and next discriminating work

This is a **failed startup/compatibility attempt**, distinct from A14/A16's
scored transport failures. No UI direction or brake cycles, no direct-control
duration, and no native/browser comparison may be credited to A17. The accepted
network scope remains Mac-shared routed local validation, not WAN/5G or vehicle
acceptance. No automatic 1441 retry is scheduled.

Further work needs a symbolized kernel crash stack and device-power/caller
correlation before another driver or firmware experiment. Future unattended
driver recovery must work without interactive logon and be revalidated after
boot; the successful SYSTEM rollback here is recovery evidence, not proof that
all future crash paths are covered.
