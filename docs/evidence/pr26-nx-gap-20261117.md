## Corrected diagnostic coverage

The Linux metadata recorder previously bound AF_PACKET to ETH_P_IPV6. On the
NX this observed inbound DTLS/RTCP but no outgoing media. The outgoing tap in
Linux uses the all-protocol packet-tap list; the recorder now uses ETH_P_ALL
while its existing parser still rejects non-IPv6 traffic and every endpoint
except the exact configured pair. See the primary
[Linux packet-socket documentation](https://www.man7.org/linux/man-pages/man7/packet.7.html)
and [kernel transmit tap implementation](https://github.com/torvalds/linux/blob/master/net/core/dev.c).
This repairs missing evidence, not the network gap itself.

Optional `--include-rtp` adds RTP sequence/timestamp/SSRC, RTCP type and DSCP
metadata. It never saves media or command payloads. Default DTLS records retain
their existing shape; RTP remains opt-in. Endpoint, direction, truncated header,
CSRC, non-IPv6, RTP/RTCP opt-in and DTLS timestamp tests passed with
`python3 scripts/test/ipv6_dtls_metadata_capture.test.py`.

A21 began with an inbound-only private recorder. A replacement using ETH_P_ALL
was started about six minutes into the scored window, verified for inbound and
outbound DTLS plus outbound RTP, then the original recorder was stopped. Both
receipts are retained. The first part has no kernel egress coverage. The private
RTP diagnostic schema and 70-minute limit differ from the default repository
tool; capture coverage must be audited explicitly. Software egress timestamps
are before physical radio delivery and must not be called physical NIC sends.

## A22 Windows internal scan correlation

Windows WLAN ETW records InternalScan with client PID0 and the exact physical
WLAN GUID. CSV's raw FILETIME places scan begin at Windows UTC
14:32:03.9245316 and completion14:32:06.0079603 (2.0834 seconds). This overlaps
the input-clear/late-command incident. Tracerpt XML printed a malformed
`+07:59` offset, so its offset was not used; raw CSV FILETIME and the recorded
Windows UTC offset are retained for independent verification.

After scan begin, Windows miniport RX gaps were approximately313/276/330ms;
miniport TX gaps remained below76ms in the inspected interval. NX kernel
ingress DTLS gap reached349ms, while aggregate RTP egress gap stayed below31ms.
Kernel capture reported zero drops/missing timestamps and maximum observer
delay4.07ms. NX radio trace recorded scans earlier but none overlapping this
failure; its trace statistics reported no dropped/overrun events. This strongly
prioritizes Windows scanning for the next intervention, without proving every
historical failure shares the same cause.

Microsoft documents that [network scanning can increase packet latency](https://learn.microsoft.com/en-us/windows/win32/api/wlanapi/nf-wlanapi-wlanscan).
The existing [media-streaming/background-scan requests](https://learn.microsoft.com/en-us/windows/win32/api/wlanapi/ne-wlanapi-wlan_intf_opcode)
reported successful at client startup, but that does not establish that no
InternalScan can occur later. No WLAN autoconfiguration change has been applied.
A separate A23 proposal is prepared with original-state readback, a protected
independent SYSTEM rollback guard, runner/heartbeat/deadline checks and normal
restoration. Disabling autoconfiguration would also affect discovery, roaming
and automatic reconnection, so it requires a user checkpoint before testing.
