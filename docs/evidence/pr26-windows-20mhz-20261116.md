# Windows 20 MHz configured-width trial, 2026-11-16

**Result: both scored AC/AX load tests failed. No 60-minute acceptance.** The user explicitly
approved this temporary bandwidth experiment. It used the previously accepted
Mac-shared routed network; this is not WAN/5G or physical vehicle acceptance.
VPN and all control/video/clock safety thresholds were unchanged. Only mock,
CAN down, confirmed zero speed/torque and five-degree steering were permitted.

## Controlled setup

A14 used the clean Windows controller artifact from runtime source
`717a348b896ba5cf3dfbaa4c38fc771d313a2862` (current PR26 head at preparation was
the documentation-only `5de0071`). All 27 controller file hashes were verified;
the same 11 UI assets, two cameras, encoding settings, Worker courier, AC radio
mode, roaming 0, and managed high-performance launcher were retained. The
runtime remained driver 3.0.1.1336. The standalone Orin signaling binary SHA256
was `c53e065fdcde5aa8a0a6d940f8cd824de5141f6f314cd676ffbc95804be6766c`;
the unchanged vehicle binary SHA256 was
`544699c324f5e6b4c49df5e420d7c94a0d4968c57954592ee62099d80c889620`.

The authorized change was `BWSelection5G: 0 (Auto) -> 1 (20MHz only)` on the
specified MT7921 physical adapter. Five-minute lost-SSH rollback and ninety-minute
restore were installed before mutation. The first guard was retired after SSH
confirmation; the restore guard remained. The normal failure/finally path also
restored Auto before restoring radio, roaming and power settings.

The read-only native query used Microsoft's
[real-time connection quality layout](https://learn.microsoft.com/en-us/windows/win32/api/wlanapi/ns-wlanapi-wlan_realtime_connection_quality)
and [link information layout](https://learn.microsoft.com/en-us/windows/win32/api/wlanapi/ns-wlanapi-wlan_realtime_connection_quality_link_info).
Both Auto and configured-20MHz queries returned `BandwidthRaw=0`, so actual
radio width is **unavailable**, not proven to be 20 MHz. The configuration was
read back as 1; before scoring, PHY was VHT/ac (8), link quality 79, RSSI -60 dBm,
and Rx/Tx rates were reported as 173300 rather than the Auto/AX baseline's
1201000. No active scan or continuous WLAN query loop was used. A fresh isolated
CA passed positive/negative TLS checks; no system trust store was modified.

## Short test result

The same real keyboard handlers exercised W/S/A/D, four diagonals and Space.
The last sample of each scenario additionally required mock gear/brake feedback,
as well as the existing steering feedback and authenticated intent correlation.
This strengthens observation and does not change input or actuation behavior.

The periodic UI samples saw a maximum RTT of only 28 ms. The complete native
send cohort includes late matching results received after the first failed
sample; those expose the long tail above. These are native publication-to-result
round trips, not physical one-way latency. A zero snapshot stop counter and a
cached ICE RTT of 3 ms do not qualify this failed arm.

Around the failure, the page recorded no long tasks, timer lag around 10 ms,
and local input HTTP elapsed time at most 12.3 ms. The two fixed probe paths
separate outbound progress from return-path delay. This does not support a
page-main-thread-only explanation.

## Windows receive-boundary evidence

The PacketMon physical-adapter receive observation and independent kernel trace
show the same vehicle-flow gap:

| Observation point | Start/end Windows UTC ms | Gap |
| --- | --- | ---: |
| Miniport vehicle UDP RX | 1794818508466.214 to 1794818510330.377 | 1864.163 ms |
| Kernel vehicle UDP RX | 1794818508466.380 to 1794818510330.571 | 1864.190 ms |
| Miniport primary-probe RX | 1794818508459.380 to 1794818510354.986 | 1895.606 ms |

During the interval, probe Tx continued at about 110 ms cadence. Each fixed
probe had 527 consecutive Tx events matching sender sequences 174–700; send-call
to-miniport-entry deltas were 1.129–18.567 ms on the primary path. The missing
primary return sequences were 635–637, despite their requests reaching the Mac.

The bounded PacketMon file was about 1.3 MB, far below its 1 GB ring limit.
Exported counts were 32125 RX/3563 TX; the pre-stop counter snapshot showed
32103 RX/3562 TX, consistent with events arriving between snapshot and stop.
Kernel export reported zero lost events. All 16 CPUs' retained DPC intervals
cover the incident; maximum recorded DPC was 0.5409 ms, with none over 10 ms.
There were zero events in the calibrated passive WLAN scan/RPC whitelist.

These software observation points locate the silence at or before the miniport
receive indication, rather than solely in the browser/Winsock application queue.
They are **not physical on-air arrival timestamps**. A driver can report late;
driver/firmware, RF and AP downlink behavior remain unresolved. This single
failed trial neither proves that 20 MHz causes the fault nor demonstrates an
improvement. The unvalidated NDIS lifecycle instrument from A13 was not used.

## Original AX mode follow-up: preparation failure (A15)

The next isolated case retained original `CurrPhyMode=0` (AX/HE) and changed
only the authorized configured width to 20 MHz, alongside the same prior
roaming/high-performance conditions. Native quality reported PHY 10 and
Rx/Tx rates 286800; actual width remained unavailable (`BandwidthRaw=0`).
The same verified 717a348 runtime and dual-camera fixture were used.

A15 did **not** enter scored control: after the real UI submitted limits, the
profile dialog remained open and the preparation wait expired after 10 s.
The raw vehicle results continued to reject with `session_profile_not_ready`;
no eight-direction control cycles were recorded. The exact UI preparation
error was not captured, so this is neither an AX+20 MHz stability result nor
evidence that a particular network fault caused the setup failure. All 345
separate gateway probes succeeded; all 1376 two-path UDP requests received
replies over the diagnostic lifetime, which extends outside setup.

At 09:33:22 UTC, readback verified original 1336, all 14 public adapter
properties, original power settings, no owned control/browser processes or
test route, and idle WPR/PacketMon with no filters. A new isolated A16 session
adds failure-only UI preparation diagnostics and retains the same conditions;
its result must be assessed independently, without concatenating durations.


## Original AX mode scored retry (A16)

A16 passed preparation and reused the same code, artifact, UI assets, cameras,
encoding, roaming and managed-power conditions as A15. Only failure-only setup
diagnostics were added to the private test harness. No safety or transport
selection threshold was changed, and driver 1441 remained uninstalled.

The sampled failure RTT was 326 ms; the full matched result cohort exposed a
425 ms maximum. Native sender wakeup lag was at most 8 ms, send calls at most
1 ms, and vehicle control mutex wait at most 1 ms. These are software round-trip
and scheduling measurements, not physical actuation or one-way latency proof.
Native publication supersession is distinct from an actual Worker send; its
unmatched publications are not counted as network loss.

The miniport vehicle RX trace contains consecutive 420.038 ms and 491.095 ms
silences. The independent kernel flow records 420.069 ms and 491.111 ms at the
same incident. Primary probe miniport RX gaps were 493.650 ms and 571.776 ms;
primary probe TX continued with no gap over 200 ms in this incident window.
The Mac observed outbound request gaps of 396.470 ms and 581.707 ms and never
received primary sequences 6006/6010. Neither a Tx software indication nor a
missing remote observation alone proves physical radio transmission/loss.

All gateway probes returned, but the incident included 292.123 ms and
426.123 ms waits. The primary returned-probe maximum RTT was 390.369 ms.
These independent flows support a fault involving the shared wireless segment,
not solely the video decoder or browser command queue. They still do not
uniquely separate driver/firmware, RF and AP behavior.

The 15.7 MB miniport capture stayed far below its 1 GB limit; its header reported
zero lost events/buffers, and its exported totals were 396166 RX/47000 TX, close
to the pre-stop 396073 RX/46993 TX snapshot. Kernel export reported zero lost
events. Retained DPC coverage across all 16 CPUs includes the incident
(1794822325908..1794822422007 UTC ms), maximum DPC 0.3287 ms, none over 10 ms.
The calibrated passive scan/RPC whitelist recorded zero events. The bounded
kernel ring does not cover the entire ten-minute test; no full-run DPC absence
is inferred. Packet traces use their own ETW time mapping; the scored UTC and
monotonic spans differ by about 76.7 ms, so cross-source wall timestamps are
not treated as sub-millisecond causality evidence. Within-trace intervals are
reported independently.

At 09:48:54 UTC, final readback again verified original 1336, all 14 public
adapter properties (including Auto width, AX and roaming 4), original power
settings, no test route, control/browser process or power journal, and stopped
WPR/PacketMon with no filters. Three inactive tasks and three dedicated
Windows auth/profile paths were removed for each of A15/A16. Orin services
were stopped, with CAN down; owned temporary keys are cleaned after archival.

Neither scored configuration satisfies 3600 continuous seconds, zero protection
and direct-control acceptance. A15's unscored setup failure and A14/A16's failed
durations are preserved separately. These trials do not establish a reliable
benefit from 20 MHz; it remains restored to Auto. A driver/firmware comparison
is the next discriminating experiment, subject to the separately pending
approval for the non-OEM 1441 trial.
