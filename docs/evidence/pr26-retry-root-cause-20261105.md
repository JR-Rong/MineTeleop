# PR #26 集成夹具重试：根因排查记录

日期：2026-11-05。范围：`cpp/tests/control_transport_integration_tests.cpp` 里三处"夹具重试"。

## 结论（先说结果）

**没有找到根因，也没有在本地复现过任何一次重试。** 三处重试保留，但现在每一次都会带原因打印并计数，
CI 日志里会直接出现证据。不要把这份记录读成"问题已解决"或"重试没有必要"：它只能说明在下面列出的本地条件下重试没有被触发。

## 三处重试

| 位置 | 触发条件 | 重试方式 |
| --- | --- | --- |
| `product_startup_and_p2p_cloud_recovery` | 车端 `safety_state == TimeoutBrake` 且最后结果为 `session_control_profile_required`，即车端 800 ms 内没有收到有效命令，真的走到了硬看门狗 | 丢弃整个夹具，用全新夹具重跑全部断言，最多 3 次 |
| `product_recovery_withdraws_unfetched_motion` 内层 | 驾驶端尚未发布非零动作，因为动作采样赶上了路由边界的重新整定 | 在 ACK 看门狗到期之前重新松键再按，最多 3 次 |
| `product_recovery_withdraws_unfetched_motion` 外层 | 待撤回的发布在检查时已超过 `kNativeBridgePublicationMaxAgeMs` | 整轮重来，最多 3 次 |

代码注释把原因归于"托管 runner 可能让发送线程被延迟一个周期以上"。这是当时在 CI 上看到的现象，本地没有留下可对照的运行记录。

## 本次做了什么

1. 给三处重试加了标记：`[RETRY] scenario=… attempt=… reason=… wall_minus_steady_ms_since_start=…`，
   每个正常返回路径前打印 `[RETRY-SUMMARY] total=N`。`wall_minus_steady_ms_since_start` 是 `utc() - steady()` 相对本进程第一次重试时的变化，
   用来判断重试是否与挂钟被调整同时发生。
2. 本地实验（Colima 虚拟机里的 Ubuntu 22.04 容器，aarch64，8 核，`--product-only` 即三处重试所在的场景）：

| 条件 | 运行次数 | 失败 | 出现重试 |
| --- | --- | --- | --- |
| 默认 | 30 | 0 | 0 |
| 8 个忙循环与测试抢 8 个核 | 20 | 0 | 0 |
| 容器限制在 2 个 CPU，6 个忙循环 | 20 | 0 | 0 |

3. 确定性实验（挂钟回拨，服务层，不依赖虚拟机的偶发行为）：让车端服务的逻辑时间倒退一段后继续按 20 Hz 送命令。

| 回拨量 | 被拒收的命令 | 之后的状态 |
| --- | --- | --- |
| 0 / 50 ms | 0 | `CONTROL_ACTIVE` |
| 100 ms | 1（`receive_time_reversed`） | `CONTROL_ACTIVE` |
| 150 ms | 2 | `CONTROL_ACTIVE` |
| 250 ms | 4 | `CONTROL_ACTIVE` |

## 已排除或不支持的假说

- **挂钟被调整导致车端走到 800 ms 硬看门狗：被证伪。** 这个环境里挂钟确实会倒退：Lima 的 host agent 会校正客户机时钟，
  日志里有 `Time sync: guest clock adjusted (was 103ms off)`，相邻两次校正相隔 30 秒；实测 45–60 秒内挂钟倒退 1–5 次、每次约 100 ms。
  在 `colima.yaml` 和 `lima.yaml` 里没有找到相关配置项（没有查阅 Lima 的文档或源码，不能断言确实没有）。
  但上表说明一次这样的回拨只会丢掉 1–2 个 20 Hz 命令，车端不会离开 `CONTROL_ACTIVE`，更到不了硬看门狗。
  （这个挂钟问题确实造成了别的偶发失败，见下一节，但不是这三处重试的原因。）
- **CPU 抢占让发送线程被延迟：本地不复现。** 8 核加 8 个忙循环、2 核加 6 个忙循环各 20 次，都没有重试。
  这不排除更小的 runner、更差的调度或不同的操作系统（Windows 托管 runner）。

## 与此相关、已经确认的环境偶发（不属于这三处重试）

- `mine-teleop-media-time-sync-retry-loopback`（`cli-over-budget`）：阶段 2 基线二进制 4/12 失败，阶段 3 之后 4/12 失败，
  空闲与满载下失败率相同。该检查比较客户端用挂钟和单调钟读到的同一次交换耗时（`cpp/src/http.cpp` 的四时间戳校验），
  与挂钟被调整的特征一致。**未对这一点做干预验证**（没有改动测试环境的时钟）。
- 阶段 3 的瞬态保持在夹具里偶发 `clock_reversed` 升级：已通过让这些夹具的车端服务使用真实 `steady_clock` 消除，42 次连续运行零失败。
  这是对"挂钟倒退会造成偶发失败"的**干预验证**。

## 如果以后要继续查

1. 推送后看 CI 日志里的 `[RETRY]` 和 `[RETRY-SUMMARY]`。有 `wall_minus_steady_ms_since_start` 的跳变，说明与时钟调整有关；
   没有跳变而重试仍发生，就是别的原因，这时 `reason=` 字段说明是哪一处。
2. 如果在 CI 上也长期没有重试，说明这些重试已经没有必要，可以删除；是否删除应由看到数据的人决定。
3. 如果重试确实发生且与时钟无关，需要对照车端 `control_hard_stop_transition` 诊断、驾驶端 trace 里的 sender 唤醒延迟和 socket 锁持有时间继续定位。
   判断是夹具调度问题还是生产代码竞态，之前没有依据。
4. 其他夹具仍然把 `utc()` 当作车端服务的单调时钟。如果它们出现偶发，先用 `steady_clock` 做干预验证。

## 2026-11-06：CI 上的瞬态保持夹具失败（原因已查明，macOS 运行器上的结果待验证）

推送 `88b0baf`、`588acd7`、`f31a932` 后，`Control darwin arm64` 里的 `mine-teleop-transient-hold-integration-tests` 三次都失败，
同一任务的其余测试通过（netem 按预期跳过）；Linux 与 Windows 的控制端任务、车端打包和 Ubuntu 全量原生测试都通过。

| 提交 | 失败的断言 | 保持时长 |
| --- | --- | --- |
| `88b0baf` | 重复尖峰场景，第三次 420 ms 尖峰 | 732 ms（前两次各约 355 ms） |
| `588acd7` | 450 ms 断流场景 | 724 ms |
| `f31a932` | 重复尖峰场景，第二次尖峰 | 715 ms |

- **初判与更正：** 第一次失败后我判断为"测试进程整体停顿"，并加了"测到停顿才重试"的包装（`e1d92a0`）。第二次失败时最大 `pump()` 间隔只有 28 ms，
  第三次是 30 ms：测试线程没有停顿，这层重试一次也没有触发过。判断是错的，重试已删除，不能说它修好了什么。
- **机制（来自 `f31a932` 的时间线）：** 断流结束后，车端把套接字里积压的命令一条条读出来，每一条都被判为 `transport_command_expired`。
  读取间隔在运行器上多数是 25–60 ms（个别接近 100 ms），而 Linux 上约 8–9 ms；驾驶端以 20 Hz（每 50 ms）发新命令，所以积压（四条以上，即 200 ms 以上的陈旧度）一直追不上，
  新到的命令也始终是过期的，保持用满 700 ms 后升级。恢复所需时间约等于积压量除以（读取速率减去到达速率）。
- **为什么是夹具：** 夹具每次 `pump()` 只读一条事件，而一轮 `pump()` 还要驱动驾驶端和 courier，运行器上要 25–60 ms。
  真实车端的原生控制 WebSocket 线程（`webrtc_media.cpp`）每轮也只处理一个事件，外加状态和结果的发送、开启时的追踪，它不驱动驾驶端或 courier。**产品侧读取积压事件的速度我没有实测过。**
- **复现**（Colima 容器，`--transient-hold-only`，给每轮 `pump()` 额外加固定延迟）：

| 额外延迟 | 旧夹具（每次读一条） | 新夹具（读空） |
| --- | --- | --- |
| 15 ms | 0/6：保持 705–713 ms，约 40 条过期命令，最大间隔 30–33 ms（与 CI 吻合） | 6/6 |
| 25 ms | 未测 | 6/6 |
| 35 ms | 0/5：2 次是场景 1 的保持 703–711 ms（约 26 条过期命令），3 次卡在启动阶段 | 0/5（当时只对保持场景读空）：4 次卡在启动阶段，到不了运动状态，1 次在对照场景 |

  35 ms 比运行器实测的最大间隔（28–30 ms）还苛刻，启动阶段的假设也扛不住，所以不作为依据。
  15 ms 的旧夹具失败特征与 macOS 完全一致；对照场景（无保持能力的车端应当制动）也依赖同样的读取速度，在改之前被前面的失败挡住，没有机会暴露。
- **没有复现的环境：** 空闲的 Apple Silicon 本机原生构建（与 CI 同参数）30/30，Linux 容器，Orin。它们的 `pump()` 一轮都足够快。
- **持续饥饿是另一回事：** 2 核加 6 个忙循环（三倍超订）下，读一条的旧夹具 0/30，后来带诊断的版本 0/10，失败方式不止一种，
  测到的最大间隔只有 77–86 ms。这是进程得不到 CPU，不是 macOS 运行器的问题。8 核加 8 个忙循环、2 核加 2 个忙循环下旧夹具各 20/20 通过。
  第一次做这组压力实验时脚本的工作目录写错，30 次全部是"找不到配置文件"，没有任何数据，改正后重做。
- **处理：** 保持场景组（含无保持的对照）的夹具每次 `pump()` 把已排队的事件读空，像车端那样；其他夹具保持每次读一条。
  失败信息附带按命令排列的时间线（每条命令的判定结果、`WSS` 命令计数、最后一条有效命令的年龄）和最大 `pump()` 间隔。不重试任何东西。
  模拟"保持恢复变慢"的变异（把保持上限压到 100 ms）在第一次就失败，仍能抓住真回归。
- **读空之后仍观察到的偶发，原因未确认：** 最终版夹具在 8 核加 8 个忙循环下共 155 次运行有 2 次失败（前 55 次里 2 次，随后的 100 次 0 次）。
  两次都是重复尖峰场景的第 4 次尖峰：上一次尖峰之后 600 ms 的稳定窗口里没有一条新鲜命令被接受，`transport_command_expired` 持续，
  而最大 `pump()` 间隔只有 15–18 ms，积压已读空，新命令按 50 ms 间隔自然到达，也就是不是排队。
  `transport_command_expired` 的判据是挂钟：`|sent_at_utc_ms − now_utc_ms| > max_command_gap_ms`（200 ms）。Colima 虚拟机会周期性步进挂钟，所以怀疑是挂钟偏差，但没有确认。
  时间线现在带 `cmd_age`（命令入场时的 `utc() − sent_at`）和 `drift`（挂钟相对单调钟的漂移），下次出现时能区分是偏差还是排队。
  之前的夹具版本在同一压力下 35 次没有失败，样本不足以判断这是不是读空引入的。
- **没有证明的：** 修复后的版本在 GitHub 的 macOS 运行器上是否稳定通过，要等推送后的 CI 才知道；这里的证据是同样的失败特征在容器里被复现、并被修复消除。
- 顺带修复：`--transient-hold-only` 路径上 `[RETRY-SUMMARY]` 被我的脚本重复打印了两次。
