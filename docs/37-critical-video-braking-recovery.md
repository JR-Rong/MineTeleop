# 关键视频制动等待与同会话恢复

## 配置与边界

- 控制端“实车调试限幅”编辑无新帧制动门限（默认 500 ms，100–3000）与制动等待上限（默认 5 s，1–30 s）。两端完整 V6、17 字段精确 ACK 后生效。修改必须停车；旧 V5/缺字段明确拒绝。
- 车端 runtime 同名字段提供默认值，页面从车端上报预填。实际执行与显示使用车端已确认的会话值。
- 关键相机已确认采集故障立即制动；无新编码帧或驾驶端无新显示帧达到门限后制动。非关键 lane 不触发该保护。
- 等待时独立安全输出撤牵引、保持当前挡位并制动，保留会话、参数修订号和控制服务。车端仍接受经过校验的零运动/制动心跳，阻止运动和换挡。
- 全部关键编码/显示恢复至少 3 帧且持续健康 300 ms 后退出等待。此前持有运动输入不会复活，需要释放、零输入、重新按下。制动保持。
- 等待期限自首次制动等待起算；偶发好帧、交替故障、lane 重开或同会话 runtime 重建不能延长期限。期限到达时即使刚收到一帧仍进入原关键视频硬停车锁存。
- 800 ms 仍从最后一个成功接受并应用的真实控制命令起算。本地制动输出不是心跳，不刷新该时钟。视频等待时控制链路也中断，800 ms 保护优先生效。
- 可定位的单路 appsrc/encoder/发送队列故障隔离该 lane；不可定位的公共管线、SCTP/DataChannel、权限/CAN/物理急停故障保留原硬安全路径。
- 相机线程与独立看门狗串行完成视频状态判断和安全输出，避免旧的健康观察交错解除新故障制动。已明确全部相机为非关键的会话不受此保护；关键配置尚未获得时驾驶端仍阻止运动。
- 本功能检测新帧和管线状态，不检查图像内容；持续有新帧的花屏、残影需编码/采集诊断，不能据此认定画面安全。

## 日志

`vehicle_critical_video_braking_wait` 和 `vehicle_critical_video_recovered` 记录生效门限、稳定时间和动作。
车端 `control_timing` 上报 `critical_video_braking_wait` 与 `driver_critical_video_ready`。
驾驶端 `control-intent` 的 `critical_video_ready` 随输入快照序号刷新，仅当前会话、token、时序合法的真实命令可改变车端视野报告。

原生反馈追踪增加：车端 delivery ACK 是否带 feedback/rearm/status 序号；云端是否收到 feedback 及其 command 序号；驾驶端 ingress ACK 是否携带 vehicle feedback、命令序号和 rearm。云端入口 ACK 本身仍不等于车端执行。
