# 校时、采集频率与硬停车复核

## 25 ms 的出处

代码默认值最早见提交 `9e5a86b`（2026-07-20，feat(runtime): add Aravis capture and synchronized clocks）：
驾驶端 `DriverConfig.max_time_sync_uncertainty_ms=25`、`time_sync.max_uncertainty_ms:25`；
车端 FieldSafetyConfig 及 loader 同样默认 25。`7a001e7`（2026-07-23）把此值写入三机
配置和 docs/07 项目规则。未找到 ISO/IEC 安全分析、车型风险评估或标准条款指定 25。
它是项目工程默认值，不是已证明适用于当前网络的认证要求。

参考 [RFC 5905](https://www.rfc-editor.org/rfc/rfc5905.html) 的误差/距离计算及滤波，
并未给 MineTeleop 规定 25 ms 或停车策略；不能把 NTP 参数当作车辆安全门限。
本项目并非完整 NTP 实现，使用 HTTP 四时间戳估计到信令云端的偏移。

当前最佳 RTT/2 是不确定度的一部分，因此必须约 RTT≤50 ms 才可能通过 25 ms。
session-000006 的拒绝组为 RTT 192/142/155/124 ms，对应 96/71/78/62 ms。
拒绝组前锚点是 390±17 ms，后续好组为 387±18 ms；偏移变化本身没有证明时钟失准，
也没有证明短时沿用旧锚点可一直安全。当前规则把一次拒绝组升级为就绪故障，
连续 5 s 未完成稳定恢复即锁会话；它对这类公网延迟明显敏感。

不能简单把两端门限提高到 100 ms：两端各±100 ms 会给命令 UTC 年龄引入至多
约 200 ms 的不确定度，与既有 200 ms 指令年龄预算相当。需要重做新鲜度证明，
或改用经验证的本地时钟/有界锚点保持；NTP 的典型频率容差不是我们硬件已验收的漂移上限。

## 修复测量与诊断

1. 客户端 T1 原本在 HttpClient 锁、DNS/TLS 之前；现在用实际 HTTP 头发送回调，
   T4 用最后响应体交付回调。互斥锁、建连和本地回调开销仍单独记录。
2. 云端 T2 原本在 API 门锁之后；现在在接收完整 HTTP 请求头/体之后、解析/路由/锁
   之前记录。T3 在业务响应准备好时记录，因此已知服务器处理等待不再冒充链路 RTT。
   线程调度发生在 recv 之前、代理排队等仍可能属于残余时间，不能宣称全是物理网络。
3. 三个低 RTT 样本的中位偏移可能移离最佳样本中心。不确定度必须覆盖“最佳样本
   RTT 半径+中位偏移移动量”；旧 max(半 RTT, 偏移离散) 可能低估边界，现修复。
4. 增加该次 HTTP 套接字的发送前/响应体接收时 TCP RTT、重传、待发/未读缓冲，
   复用既有跨平台采样。未支持字段缺省/标不可用；不记录请求 URL、凭证或头/正文。
5. 失败采样组保留已完成样本、失败下标及失败请求的时序；不完整/矛盾时间样本使
   readiness 失效，但保留上一份可信单调时钟锚点。详细数组只在校时 trace 输出。

样本中 server_before_handler_ms、server_parse_ms、server_api_gate_wait_ms 和
server_processing_monotonic_ms 可识别已知软件等待；HTTP TLS/DNS 阶段可识别建连；
TCP 重传增量支持传输异常。没有重传不等于没有网络排队。连接中间代理或主机未读
队列的贡献仍需联合同一时间窗的两端/代理记录，单端日志无法给唯一物理归因。

## 真正 20/25 Hz 采集

软件支持 cameras[].capture_fps=20 或 25，传给 V4L2 VIDIOC_S_PARM；编码 profile
fps 同设 20/25 时，不加入 videorate。已有严格 negotiated timeperframe 检查：
驱动拒绝、无效返回或仍返回 30 时显式报错，不静默冒充目标频率。

但 [V4L2 文档](https://docs.kernel.org/userspace-api/media/v4l/vidioc-g-parm.html) 允许
驱动通过跳帧实现请求。驱动交付 20 Hz 不等于摄像头传感器曝光/级联触发降到 20 Hz。
本仓库没有足够的 CCG2 驱动/传感器寄存器或外部触发配置证据证明此能力。新增日志
区分 requested_capture_fps、driver_negotiated_fps、capture_fps_observed、编码 target；
传感器频率验证仍需厂商时序/计数信息。现场默认 30 不擅自修改为未验证模式。

只读查询（不启动新采集、不修改帧率）：

```sh
v4l2-ctl --device=/dev/ccg2-channel-2 --get-parm
v4l2-ctl --device=/dev/ccg2-channel-2 --list-frameintervals width=1920,height=1080,pixelformat=UYVY
```

查询不支持也不能据此断言硬件只支持 30；需要驱动/板卡供应商确认。修改 YAML
capture_fps 与编码 fps 后，必须在停车台架上核对协商值、5 s 实测交付帧率、序号
及板卡/传感器计数。毫秒门限不随 FPS 自动延长。

## 停车触发复核

| 条件 | 当前行为 | 复核 |
|---|---|---|
| 单条过期控制 | 丢弃，不执行、不续期；默认累计 3 条要求新输入 | 不是单帧直接硬停车 |
| 没有合法且成功应用的控制 | 默认 800 ms；附件现场 2000 ms 硬停车 | 保护真实失控链路，保留；不按键可由自动零心跳续期 |
| 关键视频 500 ms 无新帧/明确故障 | 独立制动、保留会话；恢复期限默认 5 s | 关键视野持续故障应保留硬升级，非关键相机不直接锁控制 |
| 校时不可信 | 独立制动；共用 5 s 故障恢复期限，届满硬锁 | 触发不等于断网；按已确认策略保留 5 s 升级 |
| ACK 500 ms 不推进 | 原连接制动等待；健康 ACK 观察后新输入；恢复期限后重连 | 单次晚 ACK 不直接触发硬停车；真实收不到合法零控制仍由车端 watchdog 独立保护 |
| 输入租约过期 | 旧运动失效；自动新零意图可恢复，保持制动 | 不是驾驶员必须 2 s 内再次按键；避免旧长按自动复活 |
| 物理急停、制动/转向/CAN 执行或反馈故障 | 硬保护、人工检查/重新会话 | 不为测试效率放宽 |

## 已确认的校时停车策略与计时修复

保持 25 ms 运动准入与现有默认 5 s 校时故障升级规则。校时不可信立即制动；
超过恢复期限仍不可信即硬停车。即使零心跳持续到达，也不延长该期限。
本次没有引入长期沿用旧锚点的运动授权或无限校时等待。

复核发现 VehicleControlService 原本把校正后的 UTC 用于接收间隔、有效控制 watchdog
及遥测发布间隔。新锚点造成的 UTC 前跳可能误触发超时，后跳可能拒绝接收或延后
超时/遥测。现在这些实际经过时间使用 steady_clock，原 800 ms/现场 2000 ms
保护不变；只有合法且成功执行的命令能更新 watchdog。执行完成前的软件等待不
续期，记录的是命令进入接收路径的单调时刻。包内 UTC 年龄与未来时间检查仍保留。
硬停车追踪分别记录单调有效控制年龄与 UTC 诊断年龄，不把两者混为一个数。

回归需覆盖 UTC 前后跳而真实接收间隔正常、真实 800 ms 无有效命令、过期包不续期、
遥测在 UTC 后跳仍发布、客户端锁等待与服务器处理等待不计入网络 RTT、不完整
采样组保持上一锚点但撤销 readiness，以及 20/25 Hz 管线不额外丢帧。
软件/CI 回归不是硬件、实车或标准认证。

## 验证与实现复核

Docker Ubuntu 24.04/arm64、GStreamer 1.28.5、Aravis OFF 完整构建与 CTest 23/23
通过（43.52 s）；最终采样有效性标记、初始化及测试时钟改动后，控制/核心针对性
回归 2/2 通过（38.72 s），测试时钟快照恢复再由核心回归通过（2.54 s）。HTTP 请求成功/失败后清理借用的
回调、头与错误缓冲引用，保持连接缓存；错误请求后复用客户端的控制回归通过
（37.55 s）。[curl reset](https://curl.se/libcurl/c/curl_easy_reset.html) 保留连接及
DNS/TLS 会话缓存。
server.cpp 使用 CMake 生成副本，验证前显式重新配置以确保副本与当前源码一致。

- Reuse：复用现有 HttpClient、四时间戳状态、跨平台 TCP 采样、异步 trace 与
  VehicleControlService；未增加另一条控制通道或安全状态机。
- Quality：包内 UTC 新鲜度与单调经过时间分开；无完整可信组即撤销 readiness；
  旧锚点仅维持时间映射，不能授权运动。新增诊断字段可选，V7/17 profile 与 CAN ABI
  不变。原逻辑时间用例通过注入时钟运行，真实传输集成仍使用生产 steady_clock。
- Efficiency：详细校时数组最多 15 个，只随刷新日志输出；TCP 采样仅用于校时请求；
  实测采集频率复用现有 5 s 日志窗口，没有新增逐帧日志。

验收覆盖软件计时/测量与日志能力。三端新包尚未部署，真实网络与传感器 20/25 Hz
采集能力尚未验收。完整测量边界需驾驶端和云端共同更新；车端计时及采集诊断需要
更新车端包。仅有旧附件无法给网络、代理和 recv 前线程调度分配唯一延迟份额。
