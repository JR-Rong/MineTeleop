## 本轮新发现的 bug 与最小修复

视频等待期间存在**独立制动被 DEGRADED 旧输出暂时覆盖**的软件缺陷，956337f
仍存在。event 5 在 06:33:11.212–11.562 等待；旧运动 seq 806–811 为 fresh=true、
throttle=.5 / brake=0，被 rearm 门禁拒绝（runtime 203/205）。CAN 请求先为 327.6，
又在 11.239/.299/.359/.459/.499/.519/.539 变成 0（例如 CAN 59386/59416），
11.579 的 feedback 59846 仍为 VCU ready、EPB [1,1,1,1] 释放、speed 1.361 m/s。
它不是“已完成驻车后不再需要制动”。精确包→CAN 调用对应受上述时钟差限制。

源码的因果路径确定：等待启动调用 require_input_rearm → DEGRADED；
receive_command 开头 evaluate_control_watchdog 将 safety_.current_output 中保存的
旧 brake=0 发给 adapter；运动随后被 rearm 拒绝并直接返回。tick 周期虽重施安全
制动，但下一拒绝包再次发 0，所以只看最终 telemetry=1 会漏掉中间压力脉冲。
等待结束后的旧运动拒绝同样影响恢复保持。

最小修改在 evaluate_control_watchdog：仅 DEGRADED 且已有恢复等待/保持时复用
apply_recovery_brake，不发送旧普通制动值。无恢复等待的普通降级、硬 TIMEOUT、
FAULT、ESTOP、适配器硬保护与真实命令续期保持原路径。恢复仍需 fresh neutral，
新运动成功接受后才能释放制动，不恢复老按键。

回归检查完整适配器安全输出调用历史，覆盖三种恢复原因、普通压力限幅为零、
等待启动、旧运动反复拒绝、迟到/身份错误包、恢复保持与 periodic DEGRADED，
任何中间 brake<1 / 非零牵引转向均失败；拒绝不更新最后合法命令，并核验 799/800 ms
硬截止。未修复的 956337f core 在同一 Docker 夹具中 77 项通过、此新增用例在
wait startup 因中间弱制动失败；修复后 core 为 78/78，完整 CTest 为 24/24（67.67 s），
运行时诊断源契约通过，git diff --check 通过。跨平台结果以新提交的 PR CI 为准。

## 仍不确定的相机根因与新增日志

采集 sequence gap=0、capture_interval_max 约 38–43 ms、failure/reopen=0，五路均
持续采集，不能据此说物理相机拔插或采集硬件断流。编码平均约 27–28 FPS、
capture→encoded 最大约 1.535 s 且反复背压；驾驶端 TURN relay over TCP、累计
freeze 持续增加。它们支持“编码输出/接收呈现有短间歇”，但缺少逐次当刻 GPU、
raw frame 与网络内核证据，无法唯一判定硬件、GPU、编码、TCP 或接收调度原因。

新增转换事件快照而非每帧刷日志：各关键通道 capture/encoded 年龄、计数、恢复
编码基线、背压、故障与禁用状态；车端 control_service/profile/safety_state 与
完整 control_timing，包括驾驶端视频/校时/输入 readiness。记录适配器 safe_stop
调用计数前后差及 soft_brake_applied_this_transition；它只证明软件 API 成功返回，
不证明实际 EHB/EPB 完成。无控制权限时明确 readiness_observed_control_not_active，
避免把硬停后的媒体恢复看成已继续控车。

新增诊断与代码回归不是实车验收；需更新三端 V7 包后获取完整末尾 CAN、转换快照
及现场 GPU/原始帧证据，才能进一步判断剩余视频间歇与物理制动行为。
